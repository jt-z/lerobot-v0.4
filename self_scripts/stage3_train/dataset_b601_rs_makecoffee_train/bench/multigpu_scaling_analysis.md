```bash
GPU2    PXB     PXB      X      PXB     SYS     SYS     SYS     SYS     0-11,24-35      0
GPU3    PXB     PXB     PXB      X      SYS     SYS     SYS     SYS     0-11,24-35      0
GPU4    SYS     SYS     SYS     SYS      X      PIX     PXB     PXB     12-23,36-47     1
GPU5    SYS     SYS     SYS     SYS     PIX      X      PXB     PXB     12-23,36-47     1
GPU6    SYS     SYS     SYS     SYS     PXB     PXB      X      PXB     12-23,36-47     1
GPU7    SYS     SYS     SYS     SYS     PXB     PXB     PXB      X      12-23,36-47     1
```

四个关键事实：

1. **NVLink 全部 inactive** —— `nvidia-smi nvlink -s` 逐卡报 `all links are inActive`。
   RTX 3090 没接 NVLink 桥。
2. **跨 NUMA 是 `SYS`**：GPU 0–3 在 NUMA 0，GPU 4–7 在 NUMA 1。4 个 rank 的通信
   要穿主机桥 + 跨 socket 互联。
3. **GPU 4 是 PCIe Gen4 x8**，其余 x16。
4. **P2P 能力全部为 `CNS`** —— 这条是决定性事实，见 §6。

```bash
$ nvidia-smi topo -p2p r
       GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
GPU0    X    CNS   CNS   CNS   CNS   CNS   CNS   CNS
GPU1   CNS    X    CNS   CNS   CNS   CNS   CNS   CNS
...（全部 CNS）

Legend:  OK = Status Ok   CNS = Chipset not supported   NS = Not supported
```

## 2. 通信量：从估算到实测

### 2.1 v1 的估算【已推翻】

| 项 | 值 |
|---|---|
| 可训练参数 | 51,599,239 |
| 梯度体积（fp32） | **196.8 MB**（实测算术值，v1 写 206MB 略有出入） |
| Ring allreduce 每 rank 搬运量 | 2 × (N−1)/N × 196.8MB |
| v1 假设带宽 | PCIe Gen4 x16 ≈ **25 GB/s** |
| v1 推出耗时 | N=8 时 ≈ 14 ms |
| v1 推出占比 | **4–13%** |

**这个估算错了一个数量级。** 错在带宽假设 —— 本机实际只跑出 **3 GB/s**。

### 2.2 实测 allreduce【实测】

直接对 196.8MB 的 buffer 反复 allreduce，30 次取平均：

| world | allreduce 耗时 | 每 rank 搬运量 | **有效带宽** |
|---|---|---|---|
| 1 | 0.04 ms | — | — |
| 2 | 52.0 ms | 196.8 MB | 3.70 GB/s |
| 4 | 104.5 ms | 295.3 MB | 2.76 GB/s |
| 8 | **112.3 ms** | 344.5 MB | **3.00 GB/s** |

**实际带宽只有 PCIe Gen4 x16 理论值的 1/8。**

### 2.3 与训练实测对账【实测】

N=8 时单步耗时比 N=1 多出 **0.094s**，而裸 allreduce 实测 **0.112s**：

```
DDP 的重叠只消化掉 ~16%，其余 84% 全部暴露在关键路径上
```

**结论：不可扩展的开销几乎 100% 是梯度同步。**

## 3. 两个误区澄清

### 3.1 ❌「ACT 是小模型，梯度数据少，所以通信影响不大」

**这个结论是错的**（v1 里我写的是「结论对、理由错」，实测后**结论也错了**）。

正确框架确实是 comm/compute 比：

```
comm/compute  ∝  参数量 P  /  (per-GPU batch × 单样本计算量)
```

ACT 的 P 小（52M），计算/参数比确实高，**在正常互联（NVLink 或可用 P2P）上它会是通信友好的**。
但本机 P2P 不可用、带宽只有 3 GB/s，分母的优势被吃掉 —— 实测通信仍占 34%。

**教训**：comm/compute 比还要乘上「本机实际带宽」，不能只看模型结构。

### 3.2 ❌「batch 没开大 → 显存没用完 → 通信占比高」

因果链有两处问题，**且这个假设已被 batch sweep 证伪（§5.2）**：

**问题一：因果方向反了。** 显存占用和通信占比都是「batch 小」的结果，二者无因果。

**问题二：显存没用完 ≠ 算力没用完。**

| 资源 | 用量 | 状态 |
|---|---|---|
| **显存** | 6,866 / 24,576 MiB | 28%，有大量余量 |
| **算力 (SM)** | 83–100%，均值 ~95% | **接近饱和** |

**实测判决**：单卡 bs 8→24，吞吐只涨 6.5%，耗时几乎严格翻倍。**算力真饱和，batch 不是杠杆。**

## 5. Benchmark 实测（2026-09-17）

方法：固定 **per-GPU batch = 8**，N = 1/2/4/8，各 600 步，丢弃前 100 步热机，
取后 500 步的 `updt_s` / `data_s` 均值。同一天、同一机器、背靠背连续跑。

### 5.1 扩展性【实测】

| GPU 数 | `updt_s` | `data_s` | 单步耗时 | samples/s | **加速比** | **并行效率** |
|---|---|---|---|---|---|---|
| 1 | 0.181 | 0.005 | 0.186 | 43.1 | 1.00× | 100% |
| 2 | 0.209 | 0.008 | 0.217 | 73.6 | 1.71× | 85.4% |
| 4 | 0.252 | 0.014 | 0.266 | 120.3 | 2.79× | 69.8% |
| 8 | 0.265 | 0.015 | 0.280 | 228.8 | **5.31×** | **66.4%** |

**注意**：per-rank 计算量完全没变（都是 bs8），所以单步耗时从 0.186 涨到 0.280
—— 涨的 **0.094s 就是纯粹的分布式开销**。

开销随 N 的增长不是线性的，而是**早期就吃掉大头、之后饱和**：

```
相对 N=1 的单步增量:   N=2: +0.031s    N=4: +0.080s    N=8: +0.094s
```

这说明主因不是带宽随 N 摊薄，而是 DDP 固有的**每步固定开销**（allreduce + 桶同步 +
`find_unused_parameters=True` 的额外图遍历），在 N≥2 时就已经付掉了。

### 5.2 Batch sweep（单卡）【实测】

| per-GPU batch | 单步耗时 | samples/s | 显存 |
|---|---|---|---|
| 8 | 0.186 | **43.1** | 6,866 MiB |
| 16 | 0.352 | **45.5** | 12,012 MiB |
| 24 | 0.523 | **45.9** | ~18 GB |

**吞吐从 43.1 到 45.9，只涨 6.5%；耗时几乎严格翻倍。**

判决：**每卡算力在 ~45 samples/s 处饱和。开大 batch 换不来吞吐，只换来更大的
effective batch。** 显存那 72% 的余量是冗余，不是机会。

### 5.3 与真实 run 的交叉验证【实测】

| | 单步耗时 | it/s |
|---|---|---|
| fresh N=8 benchmark | 0.280s | 3.57 |
| 真实 100K run 全程均值 | 0.351s | 2.83 |

真实 run 比 fresh benchmark **慢 25%**，正好对上 §4 里 `updt_s` 单调 +25% 的劣化。
**所以那 100K 步实际多花了四分之一的时间。**

### 5.4 组拆分实验：把 8 卡拆成多个小组（2026-09-18）【实测】

**动机**：有人提出「4 卡一组、分两组跑不同策略，避免跨 NUMA 通信，让每组都拿到
近似 4× 加速」。

**结论：思路方向对，但 2×4 这个粒度不对 —— 要拆就拆得更细。**

#### 前提不成立：跨 NUMA 不是瓶颈

三条独立证据：

| 证据 | 数据 | 差距 |
|---|---|---|
| 两个 NUMA 节点各自独跑 N=4 | NUMA 0: **0.266s** vs NUMA 1: **0.273s** | **2.6%** |
| allreduce 同 NUMA vs 跨 NUMA | world=2（GPU 0-1，PIX 直连）**3.70 GB/s** vs world=8 **3.00 GB/s** | **19%** |
| 真正的根因 | **SHM 兜底本身**，对任何 N≥2 都生效（§6） | — |

NUMA 1 那组还带着 GPU 4 的 x8 半宽 PCIe，照样几乎一样快。
**拆成两组不是「避免」了这个通信代价，而是付了两遍。**

#### 实测结果（全部 600 步，同一天背靠背）

| 配置 | 单步耗时 | 合计 samples/s | 等效加速比 | 效率 | 相对 1×8 |
|---|---|---|---|---|---|
| 1×8 DDP（**单任务**，现状） | 0.280 | 228.8 | 5.31× | 66.4% | — |
| 2×4 并发（原提案） | 0.272 / 0.280 | **232.0** | 5.38× | 67.3% | **+1.4%** |
| 4×2 并发 | 0.228 | **279.8** | 6.49× | 81.1% | **+22.3%** |
| 8×1 独立 | 0.191 | **335.2** | 7.78× | **97.2%** | **+46.5%** |

**每组拿不到 4×**：2×4 时每组只有 **2.79×**（120.1 / 117.4 samples/s），不是 4×。

#### 关键前提：并发几乎不互相干扰

| 对照 | 独跑 | 并发 | 掉速 |
|---|---|---|---|
| 8×1，各卡单步 | 0.186 | 0.191（8 卡：0.188/0.193/0.193/0.188/0.190/0.189/0.189/0.199） | **+2.7%** |
| 4×2，组内 samples/s | 73.6 | 69.9 / 70.0 / 70.1 / 69.8 | **+5%** |
| 2×4，组内 samples/s | 120.1 / 117.4 | 117.5 / 114.4 | **+2.2% / +2.6%** |

**这条是结论成立的基础** —— 拆分成独立任务几乎不产生 CPU / PCIe / 供热的竞争代价。

#### 根本规律：并行效率随 N 塌陷得很快

| GPU 数 N | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 并行效率 | **100%** | **85.4%** | 69.8% | 66.4% |

allreduce 在 **N=2 时就要 52ms**，而单卡计算只要 181ms ——
**只要引入同步，第一刀就砍掉 15%。** 之后继续加卡，边际损失才变小。

#### ⚠️ 8×1 是 8 个不同的模型，不是 1 个模型

这个对照的意义是**区分两种需求**，不能无条件套用：

- **要训练单个模型**（需要全局 batch）→ 必须同步 → 5.31× 是天花板，拆组无效
- **要跑多个独立实验**（超参扫描 / 多任务 / 多个 ckpt）→ 拆开能拿回 97% 效率

具体建议见 §8.4。

## 6. 根因：P2P 不可用 → NCCL 退回 SHM【实测】

### 6.1 NCCL 走了什么路径

```bash
$ NCCL_DEBUG=INFO torchrun --nproc_per_node=8 allreduce_bench.py
NCCL INFO P2P is disabled between connected GPUs 0 and 1.
NCCL INFO P2P is disabled between connected GPUs 0 and 2.
...
$ grep -oE "via [A-Za-z/]+" nccl8.log | sort | uniq -c
     16 via SHM/direct/direct        <-- 全部 16 个通道
```

**所有梯度流量都走主机共享内存（SHM）**，即每字节都要
**GPU → 主机内存 → GPU**，过两遍 PCIe 再加 CPU 内存带宽。这就是 3 GB/s 的来源。

### 6.2 为什么 P2P 不可用

```bash
$ nvidia-smi topo -p2p r
...全部 CNS（Chipset not supported）
```

**这是硬件/平台限制，不是配置问题**：

- RTX 3090 是**消费级 GeForce 卡**，不装 NVLink 桥时 PCIe P2P 不可用
- `nvidia-smi topo -m` 早就显示 NVLink 全部 inactive
- ACS 检查：`lspci -vvv | grep -c 'ACSCtl.*SrcValid'` = **0**，不是 ACS 导致的

⚠️ **所以不要把时间花在调 NCCL 参数上**（`NCCL_P2P_DISABLE` / `NCCL_SOCKET_IFNAME` 等）。
能力矩阵是 `CNS`，NCCL 已经做了它能做的最好选择。

## 7. 哪些能线性加速，哪些不能

### ✅ 能线性扩展（∝ N）

| 项 | 说明 |
|---|---|
| 前向计算 | 每个 rank 处理自己的 batch |
| 反向计算 | 同上 |
| 单样本的数据读取 / 视频解码 | 每 rank 读自己的样本 |

### ❌ 不能线性扩展（每步固定成本，与 N 无关）

| 项 | 说明 |
|---|---|
| **梯度 allreduce** | ← **主因，占不可扩展开销的 ~90%**。通信量 = 模型大小（196.8MB），与 N 无关 |
| **optimizer step** | DDP 下每个 rank 都**完整地**更新全部 51.6M 参数 —— 完全冗余，不并行 |
| `grad_clip_norm` | 对全部梯度算一次全局范数，每 rank 各算一遍 |
| DDP 桶同步 / `find_unused_parameters=True` 额外图遍历 | 每步固定开销 |

### ⚠️ 随 N 轻微恶化

| 项 | 实测 |
|---|---|
| dataloader 竞争 | `data_s` 0.005 → 0.015（3×），但绝对值只 **+10ms**（8 卡 × 6 worker = 48 进程抢 48 核） |

### 🐢 完全串行、与 N 无关（端到端层面）

- checkpoint 写盘（rank 0，单个 591MB）
- 启动 / dataset 初始化

### 💡 但不可扩展 ≠ 无法规避

上表里「不能线性扩展」的都是**同一个模型内部**的同步成本。§5.4 实测表明：
**只要任务之间彼此独立（不需要同步），效率能回到 97%。**

```
并行效率:  N=1 100%   N=2 85.4%   N=4 69.8%   N=8 66.4%
           └─ 拆成独立任务 = 退回 N=1 的效率，再靠并发把 8 张卡填满 → 97.2%
```

关键在于**同步频率**：不用同步就没有 allreduce，也就没有那 34% 的开销。

## 8. 能做什么

> **先分情况**：下面 8.1–8.2 是**训练单个模型**的路子；如果你要跑的是**多个独立实验**，
> 直接跳 §8.4 —— 那条不需要改代码也不需要动硬件，且收益更大（+46.5%）。

### 8.1 软件：梯度累积（训练单个模型时唯一能拿回损失的手段）

降低**同步频率**。设累积步数 K：

```
samples/s = N · 8 · K / (K · 0.186 + 0.094)

K=1  : 228.6   （现状，效率 66.4%）
K=2  : 274.7   (+20%)
K=4  : 305.5   (+34%，效率 88.6%)
K→∞  : 344.1   （效率 100% 上界，+50%）
```

代价是 effective batch 变大（同样要线性放大 lr）。

> ⚠️ **lerobot 不支持梯度累积**（代码里搜不到任何实现），要做需要改训练循环。

### 8.2 硬件：NVLink 桥

3090 支持 NVLink（两两一对，8 卡需 4 对）。**这是唯一能修 P2P 的办法**，
但要主板/插槽布局配合，不确定可行。装桥后 allreduce 预计能从 112ms 降到 20–40ms，
效率有望回到 85%+。

### 8.3 不要做的

- ❌ **调 NCCL 参数** —— 能力矩阵是 `CNS`，不是配置问题（§6.2）
- ❌ **开大 batch 换吞吐** —— 算力已饱和，实测只 +6.5%（§5.2）
- ❌ **加更多卡** —— 单机已 8 卡，且效率会继续掉
- ❌ **把同一个模型拆成 2×4 跑** —— 实测只 +1.4%（§5.4）

### 8.4 运营：跑多个独立实验时拆成独立任务（**收益最大、零改动**）

**适用场景**：超参扫描、多任务、多本体对比、训多个 ckpt 备选。
**不适用**：训练单个模型（那时候需要同步，见 §8.1）。

**做法**：不要再起一个 8 卡 DDP 任务，而是用 `CUDA_VISIBLE_DEVICES` 起多个
小任务并发。实测对照（同一天、背靠背、各 600 步）：

| 拆分方式 | 合计 samples/s | 等效加速比 | 相对 1×8 |
|---|---|---|---|
| 1×8 DDP | 228.8 | 5.31× | — |
| 2×4 | 232.0 | 5.38× | +1.4% |
| **4×2** | **279.8** | 6.49× | **+22.3%** |
| **8×1** | **335.2** | 7.78× | **+46.5%** |

脚本：[`bench/run_split.sh`](bench/run_split.sh)

```bash
# 4 组、每组 2 卡（4 个任务并发）
bash bench/run_split.sh 2 600

# 8 组单卡（8 个任务并发）—— 效率最高
bash bench/run_split.sh 1 600
```

**代价与注意事项**：

| 项 | 说明 |
|---|---|
| **每任务 batch 变小** | 8×1 时每模型全局 batch 只有 8（不是 64）→ **优化动态不同，lr 需重新定**，不能无痛替换 |
| 显存 | 每组各自占用，8×1 时每卡 ~6.9GB，无冲突 |
| 并发掉速 | 8×1 时 **+2.7%**，4×2 时 **+5%** —— 很轻微 |
| 日志/产物 | 每个任务独立 `output_dir`，注意别撞名 |

> 💡 **一句话**：8 张卡要么「同步地训 1 个模型」→ 5.31×；
> 要么「不同步地训 8 个模型」→ 7.78×。**中间地带（2×4、4×2）不划算。**

### 8.5 附带待查：`updt_s` 单调 +25%

100K run 里 `updt_s` 从 0.285 涨到 0.357（r=0.892）。**这不影响扩展性结论，
但吃掉了一次 run 的 1/4 时间。** 首要嫌疑是**散热降频**（8 张 3090 密集排布跑 10 小时）。

验证：下轮训练全程采 `nvidia-smi --query-gpu=temperature.gpu,power.draw,clocks.sm`，
若 `clocks.sm` 随时间下滑即实锤。

## 9. 对「下一步」的净影响

结合 `README.md` 的结论（loss 70K 后进平台，**`eval_freq: 0` 全程无验证**）：

1. **吞吐不是当前的瓶颈，模型能不能用才是。** 首要动作仍是拿 `checkpoints/100000`
   上真机 rollout，对比 `080000` vs `100000`。
2. **训练单个模型时**，5.31× / 66.4% 在无 NVLink 的消费级 8 卡上属于正常水平，
   **不是配置失误**，也不要去调 NCCL。
3. **跑多个实验时（超参扫描 / 多任务 / 多本体对比）**，改用 §8.4 的独立任务并发 ——
   实测能拿到 **+46.5%** 的吞吐，零代码改动。这条比下面任何一条都划算。
4. 如果真机验证通过、且需要更快迭代**同一个模型**，优先级：
   先加温度/功耗采样（§8.5，零成本）→ 梯度累积（§8.1，需改代码）→
   NVLink 桥（§8.2，要动硬件）。

## 附：复现命令

脚本都在 [`bench/`](bench/) 目录下：

```bash
cd self_scripts/stage3_train/dataset_b601_rs_makecoffee_train

bash bench/run_scaling.sh        # 1) 扩展性 sweep（N=1/2/4/8，per-GPU bs=8，600 步）
bash bench/run_allreduce.sh      # 2) allreduce 裸测（196.8MB 梯度 buffer）
bash bench/run_p2p_check.sh      # 3) P2P 能力 + NCCL 实际传输路径
bash bench/run_split.sh 1 600    # 4) 组拆分：8 组单卡（§5.4，效率 97.2%）
bash bench/run_split.sh 2 600    #    4 组双卡
bash bench/run_split.sh 4 600    #    2 组四卡
bash bench/run_split.sh 8 600    #    1 组八卡 = 现状 DDP
```

| 文件 | 作用 |
|---|---|
| `bench/mkcfg.py` | 生成 benchmark 配置（`steps` / `log_freq=50` / `save_checkpoint=false` / `eval_freq=0`） |
| `bench/allreduce_bench.py` | 对 51,599,239 个 fp32 元素反复 allreduce，测真实带宽 |
| `bench/run_scaling.sh` | 扩展性 sweep，日志写到 `$BENCH_OUT`（默认 `/tmp/act_bench`） |
| `bench/run_allreduce.sh` | 各 world size 的 allreduce 耗时 |
| `bench/run_p2p_check.sh` | 输出 `CNS` 能力矩阵 + NCCL 的 `via SHM/...` 判定 |
| `bench/run_split.sh` | **把 8 卡拆成 8/G 个独立 G 卡任务并发**（§5.4 / §8.4），用于跑多实验 |

**`run_split.sh` 的输出解读**：日志在 `$BENCH_OUT/log_<标签>_g<i>.txt`，
读 `ot_train.py:444` 行的 `updt_s` / `data_s`。合计吞吐 =
`Σ (G×8) / (updt_s + data_s)`，丢弃前 ~100 步热机。

**环境**（所有实测共用）：RTX 3090 ×8，`mixed_precision: bf16`（accelerate 默认配置），
数据集 `b601_20260910_164106`，`num_workers=6`。

**读数要点**：`updt_s + data_s` 才是单步真实耗时；丢弃前 ~100 步热机；
**不要用「单步耗时」跨 N 直接比**（全局 batch 不同），一律换算 **samples/s = N×8/(updt_s+data_s)**。

> ⚠️ **基线（N=1）的测量散布约 ±2%**：600 步测到 43.1 samples/s（`updt 0.181`），
> 另一次 400 步测到 44.0（`updt 0.178`）。文中所有「效率 %」都以 **43.1** 为分母，
> 因此效率数字自带约 ±2% 的不确定度。**§5.4 的组间对比是同一会话内背靠背测的，
> 不受这个散布影响** —— 结论（2×4 无效 / 4×2 +22% / 8×1 +47%）是稳的。
